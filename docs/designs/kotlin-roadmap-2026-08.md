# Roadmap: Kotlin app support — 2026-08-24

**Goal:** apps under `examples/` can be written in Kotlin (2.1.x, `jvmTarget 1.8`) and run on the unchanged pico-jvm class-file format, on every board, with a hand-written `kotlin/**` stdlib shim merged into each Kotlin app's PAPK. The SDK stays Java. Memory is the design driver: the shim exists because the real `kotlin-stdlib` cannot run on a JVM that has 35 Rust builtins instead of a class library, and because every parsed method costs 32 B of RAM on a board where class metadata is already the largest JVM consumer.

**Process:** each numbered session below is planned and implemented in its own agentic session, sized like one substantial PR, ending in a verifiable state with `./scripts/pre-commit` green. Update the Status table and the session's subsection as work lands; divergences from this doc get recorded in AMENDMENTS at the bottom. The Session 1 inventory (`docs/designs/kotlin-shim-inventory.md`) becomes the shim's source of truth; this doc holds the sequencing and the contracts.

Written against the tree at `21e41a6` (file:line references are from that commit). A Compose-like declarative UI layer is **deferred** — see `docs/quality-roadmap.md` § Framework direction; Jetpack Compose proper is ruled out in `docs/designs/android-parity-roadmap-2026-08.md` § Not doing.

## Why now, and the numbers the design is built against

- The interpreter already runs everything javac 8 emits, including `invokedynamic` lambdas in the `LambdaMetafactory` shape (`jvm/src/interpreter/ops_invoke.rs:272-355`). kotlinc at `jvmTarget 1.8` emits the same shape for lambdas and SAM conversions, `StringBuilder` concatenation (not `StringConcatFactory`), and no condy — so Kotlin is a stdlib problem plus a short list of JVM semantics, not a new interpreter.
- The JVM has **35 Rust builtins, not a class library** (`jvm/src/native/mod.rs:44-81`): no `Object.equals/hashCode`, no `Iterable`/`Collection`/`Map`/`Set`/`CharSequence`/`Number`, `java/util/List` is a 7-method hand-rolled interface (`sdk/java/java/util/List.java`). The real `kotlin-stdlib` sits on `AbstractList`, `Collections.unmodifiableList`, `Objects`, `Serializable`, `ListIterator` and a long JDK tail — it cannot be tree-shaken into running here. A bespoke shim is the only path.
- **Memory model** (`jvm/src/class_file/mod.rs:172-215`, `jvm/src/lib.rs:302-317`): 20 B per registered class at boot (every class in the PAPK, used or not); on first touch ~88 B + ~5 B per constant-pool entry + **32 B per method**. A facade class is parsed whole, so a 35-method `CollectionsKt` costs ~2.5 KB the first time any one method is called — hence per-app method shaking (Session 2). picoenvmon today: 161 registered / 62 parsed / 41 KB metadata, ~13–16 KB live objects, **146 KB min-ever-free on device** (`docs/mem-session-2026-08.md`).
- **Budgets.** RP2040 program-flash headroom ~40 KB (`scripts/pre-commit:221-226` release gate): Sessions 3+4 together must add < 4 KB of interpreter `.text`. PAPK slot 1,020 KB usable (picoenvmon 63 KB) — not a constraint. `.bss` headroom 20.5 KB on `pico_enviro_mon_w` — no new static buffers anywhere in this roadmap.
- **Cost classes** extend the parity roadmap's taxonomy: **G** = Gradle/host only · **N** = native method on an existing class (~0.1–1 KB shared `.text`) · **B** = JVM builtin (no `.class` file) · **S** = new SDK class (~1.5–3 KB `.rodata`, on every board) · **P** = class shipped inside the PAPK (0 program-flash bytes; 20 B registration, parse cost only if touched). The whole shim is **P**; Sessions 3–4 are **N/B**; nothing in this roadmap is **S**.

## Scope decisions (settled with the project owner, 2026-08-24)

- **Proof app is a Kotlin twin, `examples/picoenvmon_kt`.** Java `picoenvmon` stays, so the RAM/flash comparison is like-for-like (`heapcensus classmeta`, `sysmon` min-free, PAPK bytes). Cost accepted: two copies of the app to maintain.
- **Shim is hand-written Java** under `kotlin-shim/java/kotlin/**`, with kotlinc's exact multifile-facade class names and JVM descriptors (`kotlin/collections/CollectionsKt`, never `CollectionsKt__CollectionsKt`). Apps compile against the *real* `kotlin-stdlib` jar for type-checking only; the shim is never on the app compile classpath and the stdlib jar is never packed.
- **Shim ships in the PAPK, never in firmware.** Program flash is the scarce resource (RP2040); the PAPK slot is nearly empty. Class metadata RAM is identical either way.
- **Kotlin 2.1.x** via `org.jetbrains.kotlin.jvm`, `jvmTarget = 1.8`, `-Xjvm-default=all` (real default methods; the JVM gains interface-default resolution in Session 4 — fewer classes than `DefaultImpls`), `-Xno-param-assertions -Xno-call-assertions -Xno-receiver-assertions`, `-Xstring-concat=inline`, `-Xno-source-debug-extension`, indy lambdas/SAM (default), `allWarningsAsErrors = true`.
- **JDK interfaces Kotlin's types *are*** (`Iterable`, `Collection`, `Map`, `Map$Entry`, `Set`, `CharSequence`, `Number`) become **name-only builtins**: a `builtin_interfaces()` table next to `builtin_super` (`jvm/src/interpreter/helpers.rs:266-303`), ~250 B `.rodata`, no boot-time registration. No new SDK `java/**` class files — interface class files are not load-bearing for dispatch (every `invokeinterface` on an object dispatches by runtime class, and builtin receivers have no class file), only for `is_instance_of` walks.
- **Out of scope:** coroutines/`suspend`, `kotlinx.*`, reflection (`::class`, `KClass`, `FunctionReferenceImpl`), `Regex`, sequences, `buildList`, constructor references (`::Foo`), method references to builtin methods (`String::length`), `data class`/`Pair` as `HashMap` keys (keys compare in Rust, `object_heap/map_store.rs:124-135`), SDK-in-Kotlin, Compose-like UI.

## Cross-cutting decisions

- **Naming.** Gradle subproject `kotlin-shim/` (`:kotlin-shim`; `sdk-kotlin` would imply an SDK surface — this is a stdlib shim that rides inside PAPKs). Plugin id `picodroid-papk-kotlin` (`buildSrc/src/main/kotlin/picodroid/PicodroidPapkKotlinPlugin.kt`, applies `org.jetbrains.kotlin.jvm` then `picodroid-papk`). Apps `examples/hellokt`, `examples/langsuite_kt`, `examples/picoenvmon_kt` — all match `newApp`'s `^[a-z][a-z0-9_]*$` (`build.gradle.kts:24`). Kotlin sources at `examples/<app>/kotlin/<pkg>/*.kt` (plugin roots `kotlin.srcDirs` at `projectDir`, include `**/*.kt`, exclude `build/**`, mirroring `PicodroidPapkPlugin.kt:39-49`).
- **Pipeline for Kotlin apps:** `compileKotlin` + `compileJava` → `stageClasses` (`Sync` of both outputs plus the `picodroidShim` configuration's classes into `build/classes-staged/`) → `stripClassMetadata` (ASM strip + shim prune/shake → `build/classes-stripped/`) → optional `shrinkClasses` → `packPapk`. `packPapk`'s single `--classes-dir` contract (`PapkPackTask.kt:59-79`, `tools/papk-pack`) is unchanged. **Java-only apps are untouched — their PAPKs stay byte-identical** (CI asserts it).
- **KGP placement.** `buildSrc/build.gradle.kts` gets `implementation("org.jetbrains.kotlin:kotlin-gradle-plugin:2.1.x")` (never `compileOnly` — plugin-classloader isolation makes it invisible at runtime) so `PicodroidPapkPlugin` can configure `KotlinCompile` directly. Known risk: Gradle 8.10 embeds Kotlin 1.9.24 for `kotlin-dsl`; if buildSrc fails against KGP 2.1 metadata, first fallback is bumping the wrapper to 8.14 (embedded 2.0.21), second is a `pluginManagement` pin in `settings.gradle.kts` with `plugins.withId(...)` reflective configuration. Session 2 settles this.
- **Strip + shake** (Session 2): ASM `ClassReader(SKIP_FRAMES)` → filtering visitor (drop `RuntimeVisible/InvisibleAnnotations`, `Signature`, `InnerClasses`, `LocalVariableTable`, `StackMapTable`, `SourceDebugExtension`; keep `LineNumberTable` + `SourceFile`) → `ClassWriter(0)` without a reader, so the constant pool is rebuilt without the `@Metadata` protobuf strings. For `kotlin/**` classes only: **prune** classes unreachable from app classes (closure over CP class refs) and **shake** unreferenced `static` methods out of classes named `*Kt` (fixpoint over shim-to-shim refs; never touch instance methods or non-`Kt` classes — `IntIterator` etc. are subclassed). `@picodroid.shim.ShimName("x")` (CLASS retention) renames a method at strip time — the javac workaround for kotlinc's return-type-only overloads such as `maxOrNull(Iterable)Float` vs `maxOrNull(Iterable)Comparable`; `@picodroid.shim.ShimKeep` exempts from shaking; `picodroid/shim/**` is excluded from output.
- **Documented divergences** (Session 8 writes the table): `mutableMapOf()`/`mutableSetOf()`/`mapOf()`/`toSet()` are unordered (`LinkedHashMap`/`LinkedHashSet` alias to `HashMap`/`HashSet`); `toString()` on builtin collections is identity-formatted; identity `hashCode()` = heap slot index, reused after GC; `@Synchronized` methods are not synchronized (`ACC_SYNCHRONIZED` is never read — blocks are fine); arrays capped at 65535 elements (`array_heap.rs:135`); `Enum.valueOf(String)` and `toTypedArray()` unsupported unless Sessions 3/4 find them cheap.
- **Budgets for `picoenvmon_kt` on `pico_enviro_mon_w`:** PAPK ≤ ~160 KB; parsed class metadata ≤ 41 KB + 20 KB; min-ever-free ≥ 120 KB (Java: 146 KB); zero `.bss` growth. Predicted: PAPK 110–160 KB (app classes ×1.2–1.4 after strip + 25–45 KB shim before shaking), +15–20 KB metadata, +1–3 KB live objects.
- **Runtime cost rule.** Every non-inline stdlib call is an interpreted `invokestatic` on a ~1 M bytecodes/s interpreter; the `-Xno-*-assertions` flags are load-bearing (otherwise every public non-null parameter costs a call per invocation). `!!` still emits `Intrinsics.checkNotNull` — that one is kept.

## Out of scope (deferred, by design)

Compose-like declarative UI (`docs/quality-roadmap.md` § Framework direction — designed once Kotlin is the language apps use); Kotlin for the SDK itself; `kotlin.test`/JUnit-style host tests for Kotlin apps (langsuite-style log-token conformance is the house pattern); Kotlin Multiplatform; an Error-Prone-equivalent static analysis lane (ktfmt formatting only; detekt is a later Amendment if warnings-as-errors proves insufficient).

### Session 3 — Interpreter I: class-file hardening, RTTI, Object/boxed identity, String canonicalization

RP2040 gate session. All in `jvm/`; unit tests as hand-assembled class bytes in the `jvm/src/interpreter/tests/invoke.rs` style, plus a Java langsuite demo. Three of these are latent bugs for Java apps too.

- `jvm/src/class_file/parse.rs:34-75` (and the `register` name scan): CP tags 17 (4 B), 19/20 (2 B) skipped by size, copied from `tools/class-shrink/src/classfile.rs:88-95`. Today a single condy entry rejects the whole class with `"unknown CP tag"`.
- `ops_invoke.rs:272-296` (`op_invokedynamic`): resolve the BSM's method handle and require owner `java/lang/invoke/LambdaMetafactory`, name `metafactory` (accept `altMetafactory` only if Session 1 (c) saw it; same first three args); anything else → a named `JvmError` (e.g. `UnsupportedInvokeDynamic`) with a host/defmt log naming the BSM, instead of misreading `arguments[1]` as the impl handle. Reject `REF_newInvokeSpecial` impl handles the same way.
- `ops_invoke.rs:53-65`: `Value::Reference(_) => "java/lang/String"` in the dispatch-class match. Today a String receiver dispatches on the CP-declared class, so `invokeinterface Comparable.compareTo` / `CharSequence.length` / `Object.equals` on a String ends in `dispatch_native("java/lang/Comparable", ...)` with no arm. `Intrinsics.areEqual(a, b)` on two Strings is the first Kotlin thing this breaks.
- `helpers.rs`: `builtin_interfaces()` table (`ArrayList → List, Collection, Iterable`; `HashMap → Map`; `HashSet → Set, Collection, Iterable`; `HashMap$KeySet → Set, Collection, Iterable`; `HashMap$Values → Collection, Iterable`; `String → CharSequence, Comparable`; boxed → `Comparable`; builtin `Iterator → Iterator`); `builtin_super` rows: boxed → `java/lang/Number` → `Object`, `java/util/NoSuchElementException` → `RuntimeException`. `is_instance_of` (`:307-350`) consults `builtin_interfaces` at every level and walks **superinterfaces transitively** through loaded interface class files, tolerating interfaces with no class file (`kotlin/jvm/internal/markers/KMappedMarker`). **Verified latent bug:** `checkcast java/util/List` on an `ArrayList` is fatal today — `is_instance_of` finds no class file, `builtin_super` has no row, returns false, and `checkcast` returns uncatchable `InvalidReference` (`ops_control.rs:188`). - `ops_control.rs:185-215`: `instanceof`/`checkcast` for `Value::Reference` (String, CharSequence, Comparable, Object) and `ArrayRef` (exact `[...` name, `Object`, `Cloneable`); a failed `checkcast` throws `java/lang/ClassCastException` via `throw_named` (catchable) instead of `InvalidReference`; lambda proxies keep working (their runtime class is the interface name).

## Session ordering rationale

Survey first because the shim inventory, the flag string, the Locale/LinkedHashMap/Number questions, and the indy-shape questions all change what Sessions 3–6 implement. Tooling second, not interpreter, because the buildSrc/KGP combination is the largest non-JVM unknown, it has zero firmware risk, and it lets Sessions 3–4 validate against real kotlinc output (`hellokt`) instead of only hand-assembled bytes. Interpreter I before II because II's default-method walk and trampoline build on I's `builtin_interfaces`/`builtin_super` tables and String canonicalization, and I fixes the fatal `checkcast` path that would otherwise mask II's tests. Shim core (5) needs both interpreter sessions (default methods for `EnumEntries`/`Lazy` interfaces, `Number` checkcast for boxing, `equals` identity for `Intrinsics.areEqual`) and the tooling (the contract test runs in the pipeline). Tiers 1–2 (6) after the contract test exists, so every added method is proven referenced. The proof app (7) needs the full shim; docs (8) need the numbers from 7. Sessions 3 and 4 are the only ones that grow interpreter `.text` and therefore the only RP2040-gate sessions.

## Risks and traps for the executing sessions

1. `!!` always emits `Intrinsics.checkNotNull(Object)`; `x as Foo` on a nullable emits `new NullPointerException(String)` inline (builtin by name — fine). The `-Xno-*` flags only remove parameter/call/receiver assertions.
2. `checkcast` today is fatal (uncatchable `InvalidReference`) for builtin receivers under interface/abstract types (`List`, `Map`, `Number`, `CharSequence`) — verified against `helpers.rs:307-350`. Session 3's `builtin_interfaces`/`builtin_super` is the fix; Kotlin unboxes `List<Int>` elements through `checkcast java/lang/Number` + `Number.intValue()`, so this sits on the hot path of every generic collection use.
3. `Value::Reference` receivers dispatch on the CP class (`ops_invoke.rs:53-65`), so `Object.equals`/`hashCode`/`Comparable.compareTo`/`CharSequence.*` on Strings fail today; `Intrinsics.areEqual` on two Strings is the first thing this breaks. Nothing in `langsuite` proves String+Comparable today (`collectionsdemo` sorts user `Item` objects).
4. `mutableMapOf()`/`mutableSetOf()`/`linkedMapOf()`/`hashMapOf()` are inline and emit `new java/util/LinkedHashMap`/`LinkedHashSet` at the call site — no shim hook; only the Session 4 alias works. Insertion order is not preserved (document).
5. `uppercase()`/`lowercase()` are inline to `toUpperCase(Locale.ROOT)`; `toUpperCase()` is a deprecation error in 2.1. Needs the Session 4 Locale handling or a documented ban.
6. `for ((k, v) in map)` and `map.forEach { (k, v) -> }` need `Map.entrySet()` + `Map$Entry.getKey/getValue`; `map.keys`/`values` already work through `HashMap$KeySet`/`$Values`.
7. String templates: non-String/primitive parts go through `StringBuilder.append(Object)`, which today appends nothing silently (`string_builder.rs:90`); `Int?` parts box to `Integer` and hit the same arm. `Any?.toString()` goes through `String.valueOf(Object)` — same trampoline.
8. `EnumEntriesKt.enumEntries` runs in every Kotlin enum's `<clinit>`: the `EnumEntries` trio is always-paid for enum users even if `.entries` is never called; `getEntries()` returns a shim `List` implementor, so `checkcast java/util/List` on it needs transitive superinterface walking (`EnumEntriesList → EnumEntries → List`).
9. `when(string)` uses `String.hashCode()` + `equals` (builtin — Java-compatible hash is already required by javac's string switch); `when(enum)` may go through a `$WhenMappings` class (`<clinit>` builds an `int[]` via `values()` + `ordinal()`, no try/catch — unlike javac's `$SwitchMap`) or a direct `ordinal()` tableswitch under K2; both fine.
10. `Companion`/`INSTANCE` init: `Outer.<clinit>` does `new Outer$Companion(null)` and initializes companion `val`s as statics on `Outer`; `object Foo` creates `INSTANCE` first, then runs its init block — nested `<clinit>` re-execution (the `clinitdemo` pattern) must hold. A companion `val` read from another class's `<clinit>` is the classic ordering bug; Kotlin semantics match Java here, so behaviour equals today's Java apps.
11. `Unit`-returning lambdas: the impl method itself returns `Unit.INSTANCE` (`Lkotlin/Unit;` in its descriptor), so `try_lambda_dispatch` needs no change; `void` SAMs (`Runnable`, `View.OnClickListener`) return `V`. The shim invoking `Function1.invoke` on a proxy goes through `invokeinterface` → `try_lambda_dispatch` (`is_virtual` covers `0xb9`).
12. `this`-capturing lambdas use instance impl methods (`REF_invokeSpecial`/`REF_invokeVirtual`); `op_invokedynamic` ignores `ref_kind` and passes captures as leading args, which happens to be correct because `this` is capture 0. `REF_newInvokeSpecial` (`::Foo`) would call `<init>` without `new` — reject in Session 3. Method references to builtin methods hit `NoSuchMethod` at `ops_invoke.rs:170-172`; callable references to Kotlin functions may compile to `FunctionReferenceImpl` (reflection) — Session 1 (a)/(b) decide the rule.
13. Kotlin `Int` in generics boxes via `Integer.valueOf(I)`; `Float` via `Float.valueOf(F)`; `HashMap<Int, ...>` keys compare by field 0 in Rust (`map_store.rs:124-135`), so boxed keys work; `Pair`/data-class keys do not (documented).
14. `Array<T>` is `[Ljava/lang/Object;` (or the typed array) and boxes; `IntArray`/`FloatArray` are `[I`/`[F`; `toTypedArray()` needs `Collection.toArray` (Session 1 (m)); `arrayOf` is inline (`anewarray`). The 65535-element cap applies (`FloatArray(100_000)` fails) — ring buffers are fine.
15. Data-class `hashCode`/`equals` use `Float.hashCode(F)`/`Float.compare(FF)`/`Integer.hashCode(I)`-style statics — Java 8 APIs the builtins lack today. Session 3, confirmed by Session 1 (h).
16. `sortedBy`/`compareBy` are inline and end in `ComparisonsKt.compareValues` → `Comparable.compareTo` on boxed values (Session 3 boxed `compareTo`) or Strings (canonicalization).
17. `first()`/`last()`/`Iterator.next()` past the end throw `java/util/NoSuchElementException`, absent today — `builtin_super` row in Session 3; `IntProgressionIterator.nextInt` throws it from the shim.
18. Interface default resolution must tolerate interfaces with no class file (`KMappedMarker` on classes implementing read-only collections) and must not parse every interface eagerly (only on a miss) — eager parsing would blow the per-class metadata budget this roadmap exists to protect.
19. `-Xjvm-default=all` is renamed `-jvm-default=no-compatibility` in Kotlin 2.2, whose default (`enable`) also emits `DefaultImpls` compatibility classes (RAM waste). Pin 2.1.x; a bump is its own Amendment. KGP forces `kotlin-stdlib` to the compiler version; never pin the stdlib separately.
20. `jvmTarget` must stay 1.8: 9+ switches string concatenation to `invokedynamic makeConcatWithConstants` (rejected by the Session 3 BSM check) and enables condy. `-Xstring-concat=inline` is the belt to that suspender.
21. `@Synchronized` methods (`ACC_SYNCHRONIZED`) are ignored by the interpreter; `synchronized(lock) {}` is inline to monitorenter/exit and works. `SynchronizedLazyImpl` uses the block form.
22. Shrink lane order is stage → strip → shrink → pack; shim classes referencing `picodroid/util/Log` get rewritten by the shrink lane like app classes, so both `sim-run.sh` modes must stay in every gate. `kotlin/**` in `keep.toml` is documentation, not a mechanism.

24. App-side metadata growth from Kotlin codegen (property getters/setters, `componentN`, `copy`, `$default`, `Companion`, `$WhenMappings`) is unshakeable; the Session 7 frugality rules exist because 32 B/method applies to app classes too.
25. `Object.hashCode` identity = heap slot index, reused after GC; `toString` identity on builtin collections prints `java/util/ArrayList@..` rather than contents (document both).
26. `Enum.valueOf(String)` on Kotlin (and Java) enums needs `Enum.valueOf(Class,String)`, absent from `enumeration.rs` — Session 3 decides cheap-or-documented.
27. buildSrc + KGP 2.1 on Gradle 8.10 (embedded Kotlin 1.9.24): metadata-version mismatch is the known failure mode; fallbacks under Cross-cutting decisions. KGP goes on `implementation`, never `compileOnly`.
28. Kotlin apps compile against the *real* JDK `java.util.List` (JDK classes shadow the SDK's `java/**` on the compile classpath), exactly as Java apps do today; the SDK's `List.java` is a runtime artifact only. Do not "fix" apparent API mismatches by editing the SDK's `java/**` files. **Update 2026-08-31 (parity T2.2):** this fact was followed to its conclusion — `sdk/java/java/util/{List,Comparator}.java` and `sdk/java/java/lang/{Comparable,Runnable,Cloneable,AutoCloseable}.java` are **deleted**. A body-less `java/**` SDK file is shadowed at compile time and never read at run time (dispatch is by receiver class, RTTI walks `BUILTIN_INTERFACES`), so it was pure flash on every board: ≈1.5 KB reclaimed. Session 4's planned `List.java: add Iterator<E> iterator()` (item below) is void. The rule is now test-enforced by `no_bodiless_java_framework_classes`; add a `BUILTIN_CLASS_NAMES` / `BUILTIN_INTERFACES` row instead.
