# `Canvas` and `View.onDraw`: a retained display list

**Status: built 2026-09-26.** Closes G4 in
[`claudeusage-gaps-roadmap-2026-09.md`](claudeusage-gaps-roadmap-2026-09.md) and item 18 in
[`claudeusage-android-shape-2026-09.md`](claudeusage-android-shape-2026-09.md), and lands T3.5 of
[`android-parity-roadmap-2026-08.md`](android-parity-roadmap-2026-08.md) in a different shape from
the one that roadmap assumed. Checked against `a2c733c0` plus this change.

## What an app writes

The Android shape, unchanged:

```java
final class TrendChart extends View {
  TrendChart(Context ctx) { super(ctx); setSize(261, 50); }

  @Override
  protected void onDraw(Canvas canvas) {
    canvas.drawRoundRect(x, top, x + 8, 50, 2, 2, paint);  // one call per bar
  }
}
// later: chart.invalidate();
```

`View(Context)`, `onDraw(Canvas)`, `invalidate()` / `postInvalidate()`; `Canvas.drawColor`,
`drawRect`, `drawRoundRect`, `drawCircle`, `drawLine`, `drawArc`, `drawText`, `getWidth`,
`getHeight`; `Paint` with colour and alpha, `Style`, stroke width, `Cap`, text size and align,
`ascent`, `descent` and `measureText`. The app-facing reference is the "Custom drawing" section of
`website/src/content/docs/api/ui.md`.

## The options, and why this one

| Option | RAM | Android shape | Verdict |
|---|---|---|---|
| `lv_canvas` pixel buffer behind `Canvas(Bitmap)` | W x H x 2: 150 KB for the display board's 320x240 panel, which has 98 KB free on its worst page (G11); about 54 KB even for one card-sized chart | exact | rejected: does not fit |
| `lv_chart` wrapped as a chart widget | small; about 10 KB of flash for `lv_chart.c` | none: Android has no chart widget | rejected: not Android, and no custom drawing |
| `onDraw` called from LVGL's `LV_EVENT_DRAW_MAIN` | none | exact | rejected, below |
| **A retained display list behind Android's API** | 32 B per draw call in LVGL's pool, 2 KB cap per view | exact at the API | **built** |

Calling Java from the draw event does not work here. LVGL renders inside `with_gfx(|g| g.tick())`
on the main task (`lifecycle/mod.rs`, `MainTask::LvglTick`), where neither the JVM nor the heap is
reachable, and every existing widget callback therefore only enqueues. The display renders in
partial mode, 20-row bands, so the event fires once per band a view crosses: a full-height view
would run its `onDraw` a dozen times per frame. And Java that touched a widget mid-render would
re-enter LVGL.

The display list keeps Android's contract where an app can see it: `onDraw` runs on the UI thread,
after `invalidate()`, before the next frame, and draws the whole view each time.

## How it works

- **Java** (`sdk/java/picodroid/view/View.java`). `View(Context)` calls `nativeCreateView` and
  makes the view's `Canvas`. `invalidate()` sets a pending flag and posts one reused `DrawTask` on
  the main executor; further calls before it runs are folded in. The task runs `performDraw`:
  `nativeBeginDraw(canvas)`, `onDraw(canvas)`, `nativeEndDraw(canvas)` in a `finally`. A released
  view (handle 0) skips. `invalidate()` on a framework widget is a no-op.
- **Binding** (`crates/picodroid-core/src/graphics/widgets/canvas.rs`). `Canvas` is in
  `picodroid.graphics` and `View` in `picodroid.view`, so `View` cannot hand the canvas its handle
  through a package-private method. `nativeBeginDraw` writes the view's handle, width and height
  into the canvas's fields from Rust, and `nativeEndDraw` zeroes them, so a canvas kept past
  `onDraw` (or one made with the public `Canvas()`) draws nothing. Every draw native reads its
  `Paint` by field slot (`graphics/fields.rs::paint`, checked by `native_field_tables_tests`);
  Java marshals nothing, since a native call costs about 30 µs on the RP2350 and a bytecode 15 to
  35 µs (D4).
- **Geometry** (`graphics/lvgl/widgets/canvas.rs`, pure functions with unit tests). Android's
  float coordinates round to pixels; right and bottom edges are exclusive; a stroke straddles the
  outline, so a stroked shape grows by half the stroke and LVGL's inward border covers Android's
  band; `FILL_AND_STROKE` is one grown fill; arcs normalise to LVGL's start and end, with a full
  turn spelled `start + 360`; a filled arc is a wedge.
- **The list** (`crates/pd-lvgl-sys/lvgl/pd_canvas.c`, compiled beside `pd_fonts.c` on every
  board that keeps `has_canvas`, which is every board but the RP2040 testbench; see Cost). Hung on `lv_obj_t.user_data`: 32-byte, pointer-free records, so the simulator's
  list is the device's size, with text copied in after its record and a font stored as a row of
  `pd_font_table`. The `LV_EVENT_DRAW_MAIN` hook replays the list with `lv_draw_rect`,
  `lv_draw_line`, `lv_draw_arc` and `lv_draw_label`. It runs after the object's own background
  (the class handler draws first), so `setBackgroundColor` sits underneath, and the layer's clip
  area is already the object's coordinates, so nothing spills out. Each op's bounds are tested
  against the band before a draw task is made. Opacity is scaled by
  `lv_obj_get_style_opa_recursive`, so `setAlpha` and a fade on an ancestor reach the drawing as
  they reach a widget. The replay only reads; Java rewrites the list between ticks on the same
  task, never during a render, which is what keeps a label's text pointer valid until LVGL
  dispatches the band.

## Found on the way

- **An exhausted LVGL pool hangs the UI task.** `lv_conf.h` sets `LV_ASSERT_HANDLER while(1);`
  and `LV_USE_ASSERT_MALLOC 1`, so any widget create that the pool refuses spins forever. The first
  cut let a view's list grow to 4 KB; `qa_ui`'s overflow fixture held that much, and the next
  `new Button` in the churn section hung the simulator at 97 % CPU inside
  `lv_obj_class_create_obj`. The cap is now 2 KB and records shrank from 40 B (a font pointer on
  64-bit) to 32 B. The hang itself is pre-existing and wider than this feature: an app that
  creates widgets until the pool runs dry gets a frozen UI with no log line. Not changed here.
- **Centred text.** A centre-aligned label of even width places its text at `(width - text) / 2`;
  `drawText` with `Align.CENTER` rounds the same way, so a row of `drawText` letters lands where
  a row of centred `TextView`s did, pixel for pixel.

  tables, the native-class registry and the API contract.
- `qa_ui` in the simulator: a `canvas` section (Paint defaults, copy, reset, alpha, text metrics;
  an unbound canvas; coalesced `invalidate`; the size a canvas reports; a removed view never
  draws; an overflowing `onDraw`; a canvas kept past `onDraw`; a resize seen by the next draw).
  202 checks, `=== ALL PASSED ===`.
- `displaydemo` has a `ShapesView` row with one of each primitive.
- claudeusage in the simulator against a replayed demo payload (`pico_display2_w`, Xvfb): the
  Limits, Burn rate and History pages of the view-per-bar build and the `Canvas` build are
  **pixel-identical** (0 differing pixels in each 640x480 window capture).
- Hardware, `pico_display2_w` (debug build with `parity-metrics`, the same replayed payload over
  WiFi): two laps of page turns by `pdb input keyevent 20`, no `slow handler` line at all, so no
  main-loop task reached 50 ms while the Burn and History charts were built and drawn.
- The contract check: `build-apk.sh --app displaydemo --board testbench_rp2040` fails naming
  `Canvas`, `Paint` and its enums; the same build for `testbench_rp2350` passes.

## Cost

Flash, release images, measured with `PICODROID_BENCH_RECORD=0 ./scripts/parity-bench.sh
--size-only --boards testbench_rp2040,testbench_rp2350`, the base being `a2c733c0` built in a
worktree with the main checkout's `Cargo.lock`:

| Board | Base | With `Canvas` | Delta |
|---|---:|---:|---:|
| testbench_rp2350 | 1,215,960 | 1,232,672 | +16,712 |
| testbench_rp2040, first cut (no gate) | 885,408 | 901,608 | +16,200 |
| testbench_rp2040, `has_canvas = false` | 885,408 | 886,940 | +1,532 |

The first cut was about three times the 4 to 7 KB estimate. The RP2040 image splits into about
8.7 KB of code and 7.5 KB of read-only data:

- **Embedded SDK classes, about 7.1 KB.** Every class ships in flash on every board. `Paint` is
  2.7 KB, its three enums 2.7 KB together, `Canvas` 1.3 KB and the draw task 0.4 KB.
- **Soft-float geometry.** The RP2040 has no FPU, so `arc_op` (1.4 KB) and `rect_op` (1.0 KB)
  are mostly floating-point library calls.
- **Dispatch.** The dispatcher arms and shims make up the rest.

That is past the 6 KB this change allowed itself on the RP2040, so the `has_canvas` board key
(`build_support/board_cfg.rs`, the `has_json` pattern) drops the classes, the Rust arms and
`pd_canvas.c` there. What stays is `View`'s own growth. On the RP2350 the dispatcher inlines the
new shims (`LvglBackend` grew 3.8 KB), and the board has 864 KB free. If the RP2040 ever needs
Canvas, the cheap cuts are integer geometry after one rounding, and plain `int` constants in place
of the enums, at the cost of the Android shape.

RAM: the list is in LVGL's pool, 32 B per op plus text. claudeusage's Burn chart is 24 ops
(768 B) where it was 24 widgets, and History's is 14 (7 bars, 7 letters) where it was 14 widgets.

## Not done

`Bitmap`, `Path`, `Matrix`, `Shader`, `save` / `restore`, clipping, `Rect` / `RectF` overloads,
elliptical ovals, a chord for `useCenter = false` fills, radii for stroked `useCenter = true`
arcs, `Cap.SQUARE`. A view resized without `invalidate()` keeps the drawing made for the old
size; the list could record its size and ask for a redraw on a mismatch, if an app ever needs it.
