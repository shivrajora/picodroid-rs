# TLS: HTTPS for `HttpURLConnection` (2026-09)

**Status: built 2026-09-27 on branch `tls-2026-09`; simulator-verified against public hosts
and the nightly's listener; device numbers in §6 as measured.** Closes the claudeusage
roadmap's G9 ("No TLS") and the app-store roadmap's S5, and supersedes its A1 measurement.

## 1. What it is

An `https` URL opens a `picodroid.net.ssl.HttpsURLConnection` (the shape of
`javax.net.ssl.HttpsURLConnection`) whose bytes travel over a TLS 1.3 session. Everything an
app knows about `HttpURLConnection` applies; the runtime does the rest at `connect()`:

- TLS 1.3 only, cipher suite `TLS_AES_128_GCM_SHA256`, P-256 key exchange (every public host
  probed accepts it; X25519 would be a second curve for no reach).
- Server name sent and checked (an IP literal is checked against the certificate's
  `iPAddress` entries and sends no SNI, per RFC 6066/6125).
- The chain verified against a compiled-in root store — 14 Mozilla roots, ECDSA and RSA
  (GTS R1/R4, ISRG X1/X2, DigiCert G2/G3, GlobalSign R3/R46/E46, USERTrust RSA/ECC, Sectigo
  R46/E46, Amazon Root CA 1; 13 KB) — plus, in a test build, the nightly's test CA
  (`PICODROID_TLS_EXTRA_CA`).
- Validity checked against the wall clock, which must be set: no clock, no handshake.
  `picodroid.net.SntpClient` (Android's hidden `android.net.SntpClient`, made public) is how
  an app sets it.
- Failures are `javax.net.ssl.SSLHandshakeException` / `SSLException` (both `IOException`s,
  served as JVM builtins like the `java.net` ones), with the reason in the message.

Boards: `has_tls = true` in board.toml, on every RP2350 WiFi board (`pico_display2_w`,
`testbench_rp2350w`, `pico_enviro_mon_w`, `pico_touch_kit`). The RP2040 has 10.9 KB of flash
left and stays without; its testbench excludes the class with the rest of `picodroid.net`.

## 2. Why this shape

The claudeusage gaps roadmap (G9) and the parity roadmap called TLS out of budget on the
RP2040 and left it "revisit as RP2350-only if a real case appears"; the app-store roadmap
(S5) picked `embedded-tls` and measured it (A1, 2026-09-04: +72 KB bare, +83 KB with a pinned
P-256 key) but stopped at "full chain verification does not build for Thumb-2" because
`rustls-webpki` pulls in `ring`. `embedded-tls` 0.19 (2026-06) has a `rustpki` feature —
X.509 chain verification with `der` + `const-oid` + `p256`/`p384`/`rsa`, no `ring`, no
allocator — which removed that blocker. The crate is pure Rust, so the simulator runs the
same TLS code as the device and the nightly can test it.

Chains probed 2026-09-27 (`openssl s_client`), which set the requirements:

| Host | Chain | Needs |
|---|---|---|
| `api.anthropic.com`, `api.coinbase.com`, `api.frankfurter.app` | P-256 leaf ← GTS WE1 ← GTS Root R4 (P-384), served with a cross-signed copy of R4 | ECDSA P-256 + P-384 |
| `api.github.com` | P-256 ← Sectigo E36 ← Sectigo E46 ← USERTrust ECC | ECDSA |
| `api.open-meteo.com` (picoenvmon's weather host), most Let's Encrypt sites | RSA-2048 ← YR1 ← Root YR ← ISRG Root X1 (RSA-4096) | RSA |
| `platform.claude.com` | P-256 ← Let's Encrypt YE2 (P-384) ← ISRG Root X2 | ECDSA |

Two facts about `embedded-tls` shaped the integration:

1. **Its `CertVerifier` takes one CA and verifies the chain from its *last* entry.** Every
   public chain above ends in a cross-signed copy of its root, so a stock verifier anchored
   at the real root fails (the last entry is signed by GlobalSign's or ISRG X1's RSA key).
   `pd_tls::PdVerifier` picks the first chain entry whose Issuer equals an anchor's Subject
   (a byte compare of the DER `Name` TLVs, which X.509 requires to be identical), cuts the
   chain there and hands that anchor to the inner verifier (the same wrapper is also where
   a multi-anchor `CertVerifier` would go if the fork ever grows one).
2. **The inner verifier keeps an owned copy of the whole received chain (`CERT_SIZE`, 8 KB
   here) and its anchor is fixed at construction.** So it lives on the heap, built once per
   handshake at the shallow point in `native_connect`, and a two-line local patch
   (`set_ca`) lets `PdVerifier` swap the anchor in. The crate is vendored under
   `third_party/embedded-tls` (`[patch.crates-io]`, like `littlefs-rust`) with three marked
   changes, listed in its `README-PICODROID.md`: `set_ca`, no panic on a malformed RSA key
   in the PSS path, and `iPAddress` SAN matching for IP-literal hosts. The copy is our fork
   for now; the patches are carried across bumps and no upstream pull requests are planned.

### The handshake and the JVM

The handshake is a second of elliptic-curve arithmetic on the RP2350, so `TlsStream::open`
runs it — and every record read and write — under `jvm_run_lock::unlocked()`, as the HAL's
own blocking calls do; the UI thread keeps running.

It does not run on the calling Java task. `rustpki`'s certificate decode and the curve
arithmetic run 24–32 KB deep (`pd-tls`'s `tests/stack.rs`, host frames), more than any Java
task has: the first device run took a HardFault inside `der::Decode::from_der` on the
interpreter's 32 KB stack, under its own frames. `net/tls.rs::handshake` spawns a
`tls-handshake` task (`TaskKind::BgWorker`, the background priority tier so it yields core 0
to the UI, `HANDSHAKE_STACK_BYTES` = 32 KB from the arena) for the one call, parks the caller
on its task notification until the task sets `done`, and takes the session back. Every
handshake logs `tls: handshake stack … unused` on the device, the figure that sizes the
constant. So `HttpsURLConnection` works from a `Thread`, a pool worker or the main thread
alike; the main thread still blocks for the handshake's length, as it would for any
`connect()`. What stays on the caller is the record layer — the software AES-GCM over every
record read and written — and that has a stack cost of its own: a 6 KB pool worker overflowed
in the AES key schedule (A2).

### Memory

Per open HTTPS connection, from the arena, freed at `disconnect()`: a 16,640 B read record
buffer (a full 16 KB record; every public front end probed ignores `max_fragment_length`),
a 4,224 B write buffer, and the connection state. During the handshake only: the provider
with the ~8.7 KB verifier. All of it `Box`ed with fallible reservation for the two buffers;
the crate's SIMD-aligned types are kept off the heap (an HMAC-SHA256 counter DRBG instead
of ChaCha, and the host builds use the software AES/POLYVAL backends — `.cargo/config.toml`
— so the simulator's align-8 tripwire models the device heap; `pd-tls` has a test for it).

### Policy: no clock, no handshake

The inner verifier skips the validity check when the clock answers `None`. `PdVerifier`
refuses instead (`Failure::NoClock` → `SSLHandshakeException("wall clock not set; sync the
time first (SntpClient)")`). Android has a clock; an app on a picodroid board sets one.

## 4. The examples

`https_get` (the nightly's `net` row): SNTP, then a GET against the test listener, three
handshakes with the listener that must be refused (expired leaf, untrusted CA, wrong name),
then `api.anthropic.com` (ECDSA) and `api.open-meteo.com` (RSA), logging status and
handshake time. Only the local legs are asserted; the public ones need the internet.

`askclaude` (the showcase): A/B pick a prompt, X sends it to the Messages API, the reply
fills the screen with the round trip and token usage on the status line; on the Enviro+
board the prompt carries the room readings. The key and model are `BuildConfig` constants
(`PICODROID_ANTHROPIC_API_KEY`); the nightly points the endpoint at the listener's canned
`/v1/messages` and presses X through `test.ctrl`.

## 5. Not done, by choice

- `SSLSocket` / `SSLSocketFactory` (raw TLS sockets): nothing needs them yet; the session
  type is ready for it.
- Session resumption, client certificates, ALPN, HTTP/2: no.
- A `pdb prefs set` verb for runtime provisioning of a key: the `BuildConfig` route covers
  the showcase; see the askclaude README for the trade-off.
- claudeusage direct-API mode: evaluated and dropped (the Claude Code OAuth token would
  have to live on the device with its own refresh cycle, and the History page cannot be
  served by any API); the bridge stays. Recorded in the evaluation plan.

## 6. Measurements

Host (simulator, x86-64, 2026-09-27): handshake to `api.anthropic.com` 10–17 ms, to
`api.open-meteo.com` (RSA-4096 root) 340–510 ms, `api.github.com` 24 ms.

Device (`pico_display2_w`, release, helloworld image, `parity-bench.sh --size-only`):

| Image | Flash (program region) | RAM (.data + .bss) |
|---|---|---|
| without TLS | 1,587,892 B (75 %, 509,260 free) | 419,864 B |
| with TLS, ECDSA only (`pd-tls` without `rsa`) | 1,859,876 B (88 %, 237,276 free) | 419,864 B |
| with TLS, ECDSA + RSA (shipped) | 1,916,532 B (91 %, 180,620 free) | 419,864 B |

The full client costs **328,640 B** of flash — twice the evaluation plan's estimate — and no
static RAM: everything TLS allocates is per connection, from the arena. RSA is 56,656 B of
it (as estimated); the surprise is the ECDSA base, 271,984 B. By crate, from the ECDSA-only
image's symbol table (`arm-none-eabi-nm --size-sort`, symbols attributable by name):

| Crate | Bytes | Note |
|---|---|---|
| `p384` | 80,804 | fiat-crypto field and scalar arithmetic, 64-bit limbs unrolled for a 32-bit core; `Scalar::invert_unchecked` alone is 20 KB |
| `sha2::sha512` | 27,748 | SHA-384, only P-384 needs it |
| `rustpki` + `der` | 47,620 | X.509 parsing |
| `embedded-tls` | 33,804 | the state machine, record layer, extensions |
| ecdsa / elliptic-curve / primeorder / crypto-bigint | 15,952 | |
| `p256` | 10,552 | |
| `net::tls` (picodroid-core) | 9,700 | |
| sha256 / hmac / hkdf | 9,198 | |
| aes-gcm | 7,790 | |
| `pd-tls` | 3,530 | plus 13 KB of root DER in `.rodata` |

So P-384 is 109 KB of the 272 — the price of anchoring at the real roots (GTS Root R4,
USERTrust ECC, ISRG Root X2 and the Let's Encrypt YE intermediates all sign with P-384).
Anchoring at the P-256 intermediates instead would drop it, at the cost of chasing every
intermediate rotation; not done. The levers that keep the roots are below (§7).

Device (`pico_display2_w`, debug-profile firmware at opt 3, `https_get`, 2026-09-27; the
test listener on the bench PC, WiFi):

| Leg | Handshake | Note |
|---|---|---|
| test listener, P-256 leaf under the test CA (2 certificates) | 1,129 ms | |
| `api.anthropic.com` (P-256 leaf, P-384-signed intermediate; anchor GTS Root R4) | 1,180 ms | one P-384 verify |
| `api.open-meteo.com` (RSA-2048 leaf and intermediates, RSA-4096 root) | 1,993 ms | three RSA verifies + PSS |
| expired / untrusted / wrong-name ports | refused | the intended reason each time |

Handshake task stack: **32,760 B used** of a 64 KB measuring stack, identical for the
P-256, P-384 and RSA chains — the peak is `rustpki`'s certificate decode (`der` frames), not
the curve or bignum arithmetic; a chain refused before the inner verifier (no known root)
peaked at 12,752 B. `HANDSHAKE_STACK_BYTES` is 40 KB; the confirming run on it logged
`40960 B, 8200 B unused` on every leg (local 1,151 ms, Anthropic 1,409 ms, open-meteo
1,991 ms) with 104.7 KB minimum free heap (80.7 KB under the 64 KB measuring task). SNTP round
trips 7–156 ms.

## 7. Amendments

### A1 (2026-09-27) — flash: what did and did not shrink it

The evaluation plan gated the spike at a 250 KB flash delta; the measured client is 329 KB
(§6). Levers tried and open:

- **Per-package `opt-level = "s"` for the crypto crates: no effect** — 1,914,736 B against
  1,916,532, 1.8 KB. The device profiles use fat LTO, which re-optimizes every crate at the
  binary's level, so a package override only changes the pre-LTO codegen. (A global "s" was
  priced out on the JVM in flash-budget-2026-09.md §6.1 and stays out.)
- **Drop RSA** (`pd-tls` without its default `rsa` feature): −56,656 B, loses every Let's
  Encrypt RSA site (open-meteo, most of the web). A board could opt out through a
  `tls_rsa = false` key if one ever needs the flash; not wired.
- **Drop P-384** and anchor at the P-256 intermediates (GTS WE1, Sectigo E36, …): −109 KB
  (`p384` 81 KB + `sha2::sha512` 28 KB), at the cost of re-shipping the store every time an
  intermediate rotates. Rejected while the roots fit.
- **A leaner P-384**: `p384`'s fiat-crypto arithmetic is 64-bit-limb code unrolled for a
  32-bit core. A Cortex-M assembly kernel (`mcu-crypto-asm` publishes audited P-256/P-384
  kernels with a Rust fallback) would cut most of the 81 KB and speed the handshake; it is
  the lever to pull if the program region gets tight. Not done.

The region stands at 91 % on `pico_display2_w` with the launcher, settings and TLS linked
in; the app-store slot arithmetic (S1) must count TLS at 329 KB.

### A2 (2026-09-27) — picoenvmon's weather over HTTPS, the `weather` example, and a sim starvation

`picoenvmon` (both twins) now fetches its open-meteo weather row over `https`: the URL, an
`SSLHandshakeException` log line, and the fetch waits for the NTP sync the certificate check
needs (`weather: waiting for the clock`, then the next housekeeping job). The new
`examples/weather` is the phone-style app for `pico_enviro_mon_w` (today with an hourly strip,
the week, details with the room's own readings; one request every 15 minutes on its own
`Thread`, glyphs and lists as `onDraw` recordings, the sky a `GradientDrawable`), with a
`net` row against the listener's canned `GET /v1/forecast`.

The move found a simulator-only hang. picoenvmon's fetch runs on a pool worker while its
dashboard thread sits in `accept()`; in the simulator that accept is a host `poll()`, which
FreeRTOS's POSIX port cannot see as blocking, so the Java thread (the JVM tier, priority 15)
stays the running task through every accept timeout and the `tls-handshake` task, spawned at
`PRIORITY_BG_6`, never got its first slice (gdb: parked in `prvWaitForStart`; the caller parked
on its notification forever, no timeout in play). Pool workers share the JVM tier, which is
why the NTP job on the same worker always ran, and why `https_get`, `askclaude` and `weather`,
with no serve loop, never showed it. On the device the same accept blocks inside FreeRTOS+TCP
and the BG tier gets the idle time §3 assumed. `net/tls.rs::HANDSHAKE_PRIORITY` is therefore
`PRIORITY_JVM_NORM` under `cfg(any(feature = "sim", test))` and `PRIORITY_BG_6` otherwise;
the general trap (any task below the JVM tier can starve behind a Java thread in a simulator
socket call) is noted there and in the scheduling audit's follow-ups.

Two device findings on `pico_enviro_mon_w` (Pico 2 W with the Enviro+ pack, debug
profile, 2026-09-27), the heap-constrained board §6 never measured:

- **The arena was 1 KB short of the transient.** With 118 KB free at idle, the first fetch
  from either app died on `Box::new(HttpConn)` — the HTTP client's 1 KB connection object,
  allocated right after the handshake, while the handshake task's 40 KB stack is still held
  (a self-deleting FreeRTOS task's stack is reclaimed by the idle task, later), the 16.6 + 4.2 KB
  records are live, the fetch thread's 16 KB stack (weather) and the TCP window buffers too.
  Two changes: the board runs two pool workers instead of four (12 KB back; picoenvmon posts
  one housekeeping job at a time), and that box is a fallible allocation, so the same state
  now ends in an `IOException` for a fail-soft caller instead of a HardFault.
- **A 6 KB worker cannot carry the record layer.** picoenvmon's fetch runs on a pool worker;
  its handshake completed (40 KB task, 8,200 B unused as on `pico_display2_w`) and the first
  record read hard-faulted in `aes::soft::fixslice32::aes128_key_schedule` — the AES key
  schedule's frame on top of the interpreter's. The board's workers are 8 KB now (two of
  them: 8 KB less arena than the four 6 KB ones), which carries the reads; the close did not
  fit even so — `close_notify` goes through the record encoder, whose `ClientRecord` local
  sits on the stack with the AES-GCM key schedule, and the worker faulted there with about
  3 KB spare (twice: once moving the connection out of its box to close it, then, with the
  fork's fourth patch `TlsConnection::close_notify(&mut self)`, in the cipher construction
  itself). The alert is optional for an exchange that is complete, so `TlsStream::close`
  sends it only when the calling task has `CLOSE_NOTIFY_STACK_BYTES` (8 KB) spare, from the
  same stack probe the handshake logs, and otherwise drops the session and logs
  `tls: closing without close_notify`; the 16 KB Java thread of `weather` sends it, the pool
  worker does not.

| Leg | Result |
|---|---|
| `weather`: first fetch after SNTP, on its own `Thread` | 2,439 ms for the request, reply and parse; handshake stack 8,200 B unused |

| `picoenvmon`: weather row on an 8 KB pool worker | `weather: Mainly clear +19C`; the worker's stack high-water 1,828 B spare (22 % headroom, the board's standing exception to the 25 % rule); close-notify skipped |
| `picoenvmon`: arena, `pdb sysmon` after the fetch | 98.4 KB free at rest, **3.4 KB minimum** during the fetch |

The last row is the budget on this board: the fetch's transient is about 95 KB of the arena
(the 40 KB task stack, the 8.7 KB verifier, the 21 KB of records, the certificate flight in
FreeRTOS+TCP buffers, the socket, the reply on the JVM heap), against 98 KB free at rest.
Everything on that path is a fallible allocation or a C-side one that reports failure, so a
dashboard request landing mid-fetch degrades to an error rather than a fault, but the margin
is thin and two levers are open: reclaiming the handshake task's stack as soon as the
handshake ends (a self-deleting task's stack waits for the idle task; a `task_delete` on the
RTOS seam would free it before the HTTP exchange, which is where the first fetch died) and a
re-derivation of the board's JVM `prereserve_*` claims, sized in August with generous margins.
The `weather` example, with no dashboard and a 16 KB fetch thread, sits about 4 KB better.
