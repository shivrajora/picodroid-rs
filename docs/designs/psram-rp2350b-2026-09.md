## Short answer

**Feasible, and worth doing eventually — but not for the reason it looks like.**

The Pimoroni Pico Plus 2 W carries an 8 MB APS6404L on GP47, sixteen times the
520 KB of on-chip SRAM. The obvious move is to put the Java heap there and stop
worrying about memory. That is the one thing worth *not* doing first.

Three facts shape this:

1. **PSRAM is not SRAM.** It is reached over the same QSPI bus and the same XIP
   cache as flash, at a fraction of on-chip bandwidth and with a cache miss
   costing hundreds of cycles. Anything the interpreter touches on every
   opcode — the operand stack, the slot arenas, the object headers — would pay
   that on every miss.

2. **The JVM heap is the hottest thing in the system.** Moving it wholesale to
   PSRAM trades a memory problem nobody currently has on this board (16 MB of
   flash, 408 KB of arena, the roomiest board on the bench) for a throughput
   problem on every workload.

3. **The things that would benefit are cold and large**, and picodroid has
   exactly two of them: the LVGL render pool and the loaded-class bytes. Both
   are read in bulk, both are big enough to matter, and neither sits in the
   interpreter's inner loop.

So the useful version of this work is narrow: put the cold, large consumers in
PSRAM and leave the interpreter where it is.

## What enabling it costs

Three pieces, none of them large on their own.

**Boot.** The RP2350's QMI has a second chip-select window, and the bootrom
does not initialise it. Bringing PSRAM up means driving GP47 as `XIP_CS1`,
issuing the APS6404's enter-quad-mode sequence, and programming the QMI timing
registers for the part. It has to happen before the allocator is asked for
anything, which on this family means inside `platforms/rp/src/hal/rp/boot.rs`,
before the FreeRTOS arena is handed out.

**The linker.** `mcus/rp/rp2350b.x` gains a `PSRAM` region at 0x11000000, and
`build_support/flash_layout.rs` gains a `psram_kb` MCU key alongside `flash_kb`
and `ram_kb`. That file currently models one flash and one RAM region; a third
is a genuine extension of its geometry, not a parameter.

**The XIP window discipline.** This is the part that will bite. Runtime flash
writes already run with XIP disabled, from RAM, with core 1 parked — the
`with_xip_disabled!` rule in `hal/rp/flash.rs`. PSRAM shares that window. Any
code holding a live pointer into PSRAM across a flash write reads garbage, and
the failure is invisible in the simulator, which has neither. Every existing
`with_xip_disabled!` site would need auditing for PSRAM reachability, and the
rule would need restating: *nothing in PSRAM may be live across a flash write*,
which for the installer means the app image cannot be staged there.

## What should live there

In the order their case is strongest.

**The LVGL render pool** (`LV_MEM_SIZE`, 64 KB today, a static array in `.bss`).
It is the single largest static consumer on the board, it is touched by the
renderer rather than the interpreter, and freeing 64 KB of `.bss` hands that
much back to the core-0 main stack — the budget that `MAIN_STACK_FLOOR_BYTES`
guards and that the W boards' debug images already faulted on once. Moving it
would also lift the cap that keeps focusable list rows under about twelve on
the 48 KB boards. The risk is that LVGL allocates draw buffers from this pool
during rendering, so the throughput cost needs measuring before, not after.

**The loaded class bytes.** Framework and app classes are read once at load and
then walked. A `--shrink` image's framework classes are around 200 KB. This is
the cleanest fit for a cold, large, read-mostly consumer.

**Not the JVM heap, and not the operand stacks.** See above.

## What it would buy this board

Nothing urgent, which is why it is deferred. `pico_touch_kit` has 2 MB of
program region, 4 MB of filesystem and 10 MB of app region, and its 408 KB
arena is the same one every RP2350 board runs on. The board that would benefit
most from this work is `testbench_rp2040`, which has none.

The honest case for building it is a future board with a larger panel or a
larger app, not this one.

**2026-09-11: this section is the part that aged.** Scrolling the Set-time
screen runs at 3-8 fps, and the two cheapest structural fixes — double-buffering
the band transfer, and turning `LV_OBJ_STYLE_CACHE` on — are both blocked by
RAM sitting at 97.7 % (520,304 / 532,480 B, ~12 KB free). Moving the 64 KB LVGL
pool out of `.bss` is what unblocks them. Details and scope in §5 and §7 of
[scroll-performance-2026-09.md](scroll-performance-2026-09.md).

## Stages, if it is built

1. Bring PSRAM up at boot and prove it: a power-on test that writes and reads
   back a pattern across all 8 MB, reported through `pdb sysmon`.
2. Add the `PSRAM` linker region and the `psram_kb` MCU key.
3. Audit every `with_xip_disabled!` site for PSRAM reachability, and state the
   rule in the porting guide beside the existing flash-write rule.
4. Move the LVGL pool behind a board.toml opt-in, and measure the render
   throughput cost on the bench before making it a default anywhere.
5. Only then consider the class bytes.

## Open questions

- Whether the QMI's second chip select can be programmed without disturbing
  flash XIP timing on the first, which the boot code must not break.
- Whether LVGL's draw-buffer allocations out of `LV_MEM_SIZE` make the render
  pool a bad first candidate after all. Stage 4 measures this before committing.
- What the simulator does. It models neither PSRAM nor the XIP window, so a
  PSRAM-reachability bug is hardware-only — the same class of bug as the 32-bit
  handle dangles, and it will need the same kind of on-device test to catch.
