# QA round — 2026-09-13

A second sim-driven QA round after the multi-app work: seven new self-checking apps
(`examples/qa_*`) were written against the served API surface, run on the simulator with the
handle sanitizer and the device heap model on, and every failure was traced to an OS defect, a
documented divergence, or a mistake in the app itself. Each defect was fixed in its own commit and
re-verified on the sim and on the bench boards. The nightly cron jobs were suspended for the night
so their runs could not interfere (auto-restored the next morning).

Method per finding: reproduce in the QA app → decide OS bug vs. divergence → fix (with a unit test
where the crate has a harness) → the app goes green → commit → hardware. Ids: `J*` = jvm crate,
`F*` = framework core / SDK.

## The apps

| app | covers | checks |

| `qa_coll` | identity hash across GC, HashMap growth and views, boxed keys, ArrayList, HashSet, `Arrays`, string edge cases, `String.format`, StringBuilders, wrappers, `Random`, OOM recovery | 385 |
| `qa_store` | files, streams, directories, refused paths, `Context` file helpers, SharedPreferences (limits, commit at the cap), StatFs, a marker that must survive to the next run | 134 / 135 |

| `qa_life` | intent extras of every type, `startActivityForResult`, service start/bind from two activities, async service steps one per frame, a burst of transitions, prefs shared across activities | 74 |

Every app logs `FAIL: <check>` / `CRASH in <section>: <throwable>` and ends with
`=== ALL PASSED ===` or `=== FAILED: … ===`; `scripts/hil-tests.conf` has a `term` row per app
waiting for the former. Documented divergences are logged as `known divergence: …`, not failed.

Bench-side, the QA apps run on every board in both shrink modes through `hil-run.sh`; see
[Hardware verification](#hardware-verification). J22–J25 were found only there: the sim's device
heap model is the RP2350's, and the RP2040 (160 KB) and the touch kit (LVGL draw buffers) are
tighter than it, so every infallible allocation in a native path is a board reset waiting for a
big enough app.

## App mistakes found on the way

Worth recording because the next round will make them again: `HashSet` arithmetic off by one
(`999 − 899 = 100`, not 99); a 5000-element boxed list and a 1200-entry boxed map do not fit the
device heap model (408 KB, framework included — keep collections to a few hundred boxed entries
and run the OOM probe last, since the fragmentation it leaves disturbs later sections); Java 8's
`Double.toString` is not always the shortest representation (`1.2345678901234567e22` prints as
`…568E22` on JDK 19+ and here); the `ScrollView` row loop and the churn loop both said `40`, so a
"replace all" on the constant would have broken the wrong test; Error Prone's ERROR tier rejects
`==` on boxes, `array.equals`, format strings with the wrong arity and a few other things a test
deliberately wants to write — cast to `Object` or compute the string first.
On a device the LVGL clock advances per UI tick and lags wall time on a display-less board, so
a 120 ms animation was not over 600 ms after it started on `testbench_rp2350` (end action unfired,
translation at 7 of 20): a check that depends on an animation ending must poll for the end action
(bounded), not sleep a fixed time.
Running `hil-run.sh` for two boards of the same MCU family from one worktree at the same time
races them on the shared `target/<triple>/release/picodroid` — one board can be flashed with the
other's image (the Pico 2 W once booted a touch-kit build, probing PSRAM and a GT911 that are not
there). Run same-family boards one after the other, or through `hil-fleet.sh`, which gives every
slot its own target directory; the RP2040 (thumbv6m) is safe to run alongside either.

`qa_thr` lists the boards it runs on (`testbench_rp2350`, `testbench_rp2350w`, `pico_enviro_mon_w`):
the RP2040 boards exclude the `picodroid.concurrent` classes from their framework by design, and
the touch kit has less thread RAM left than its executor sections need.
`qa_coll` lists `rp2350,rp2350b`: its working set outgrows the RP2040 testbench's heap in the strings
section (genuine `OutOfMemoryError`s from there on, no reset once J23 and J26 are in), as the langsuite
rows already do; so does `qa_store`, whose directory matrix (ten directories, two 4 KB LittleFS
blocks each) does not fit the RP2040 testbench's 128 KB volume — every write past the first few
fails there; and so does `qa_ui`: its widget tree runs the RP2040 out of heap in the containers
section (an `OutOfMemoryError` now, then one infallible 10 KB allocation in the focus section that still
resets the board — noted below).

## Divergences kept (documented, logged by the apps)

- Reference arrays carry no element class: no `ArrayStoreException`, `String[] instanceof
  Integer[]` is true, `(String[]) objectArray` succeeds (compatibility matrix, unchanged).
- Strings are byte-backed ASCII: `new String(utf8Bytes)` renders a non-ASCII byte as `?`.
- The subnormal minima print as their shortest form: `Double.MIN_VALUE` is `5.0E-324` (Java:
  `4.9E-324`), `Float.MIN_VALUE` is `1.0E-45` (Java: `1.4E-45`).
- A precision on an integral conversion throws `IllegalFormatException`, the family's base class,
  rather than `IllegalFormatPrecisionException`.
- `removeView` / `AlertDialog.dismiss()` free the widget; a removed view or dismissed dialog cannot
  be re-added or re-shown (`IllegalStateException`), where Android keeps them usable.
- `HashMap`/`HashSet` never consult `hashCode()`; equality is `equals()` over a linear buffer.

## Follow-ups

- LittleFS opens allocate their 4 KB file cache infallibly: on the RP2040, once qa_store had filled
  the volume and thrown a dozen `IOException`s, the next open reset the board with "memory
  allocation of 4096 bytes failed". The stream arms could reserve it fallibly like everything else
  in this round.
- **Open: qa_life stalls intermittently on `testbench_rp2350` (the Pico 2 W slot), both shrink
  modes, roughly one run in two.** With the timer instrumented, the step after a Service
  re-creation is armed and posted (no "queue full" drop, no Runnable error once F11 logs them) and
  the UI loop never runs it; the runs that stall are the ones whose pending-op drains took
  100–260 ms just before. The sim, the RP2040 and the touch kit never stall. Two candidates are
  left, and a run with `rtt-lossy` (non-blocking RTT, `defmt-rtt` recompiled) stalled the same
  way, which rules out RTT back-pressure: the main task does not wake from `recv_blocking` for a
  child task's post on that board — the Pico 2 W's second core carries the cyw43 task and the
  flash parker, and this is the same neighbourhood as the reverted WP7 tick-clock change and its
  W-board tick stall. On a freshly formatted volume the shrink build passed all 74 checks while
  the no-shrink build stalled again after `Svc.onUnbind`, so the volume is not a factor. A `pdb`
  stack dump of the main task during a stall is the next step; the touch kit (RP2350B) and the
  RP2040 never stall.
- Explained (bench, not OS): the same slot's later storage failures — qa_life's "prefs written by
  C visible in A" and a qa_store run that could not write at all — boot with
  `[fs] init failed: invalid parameter`: the touch-kit image that the parallel-run race flashed
  onto the Pico 2 W left the LittleFS region formatted for that board's geometry, and the
  testbench firmware neither mounts nor reformats it. A chip erase restores it; the runtime could
  treat a geometry mismatch like a missing superblock and format.
- With J25 the touch kit's qa_thr run reports `OutOfMemoryError("unable to create native thread")`
  from its latch and executor sections instead of resetting, but one infallible 7680-byte allocation
  remains on the path a background-pool worker takes into Java under a full heap (it is not the frame
  or the task stack); it needs a device heap census to name.
- Every bench board runs the legacy 32-bit handle cast, so the sim's stale-handle answers
  (`Reparent::StaleChild`, `is_live`, the sanitizer) are device use-after-frees until
  `handle-table-32` ships; F10 moved the release state to Java for that reason. The staged table
  deserves its soak now — the QA app's tree section is a ready-made check.
- The RP2040 intrinsic finding (J22) is platform-wide: picodroid-core's own `as i32` casts of a
  negative fraction (animation offsets, sensor scaling) floor on that board too. The durable fix is
  at the HAL level — truncating `__aeabi_*2iz`/`2lz` symbols in place of the bootrom mapping, or
  rp2040-hal's `disable-intrinsics` at the cost of the ROM float speed-ups — and is left for a
  measured decision.
- The RP2040's 160 KB heap holds far fewer boxed entries than the sim's device model; the QA
  apps are sized for it, but an app that grows a collection past a few hundred boxes should
  expect `OutOfMemoryError` there first.
- `IllegalFormatPrecisionException` (and the rest of the `IllegalFormat*` family) could be given
  their own class names cheaply now that the formatter distinguishes the cases.
- The legacy 32-bit handle cast (no table) cannot tell a released handle from a live one, so a
  double `dismiss()` after a keypad BACK is still a dangling pointer on a device until
  `handle-table-32` ships; the Java-side handle release covers the app-driven cases.
