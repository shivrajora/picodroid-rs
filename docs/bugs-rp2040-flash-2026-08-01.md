# Bug backlog: rp2040 runtime-flash failures — 2026-08-01

Two failures found on a real **testbench_rp2040** board (RP2040, Waveshare 2.8"
Pico display) when the rp2040 half of the HIL gate was run for the first time.
Both sit on the **runtime flash-write path**, and both are **pre-existing** —
they reproduce identically at `e44b879`, before the work that surfaced them.
Neither reproduces on RP2350.

Each section is self-contained: symptom, evidence, repro, attribution, and what
to check first. RP40-1 and RP40-2 are probably one root cause (see
[Shared hypothesis](#shared-hypothesis)) and are best worked together.

**Status: FIXED — verified on `testbench_rp2040` 2026-08-10, RP2350
regression-swept on `pico_enviro_mon` 2026-08-11.** Both bugs were one
symptom-pair with a stack of three cooperating root causes; see
[Resolution](#resolution-2026-08-10) at the end. The observation/hypothesis
sections below are kept as written — the shared hypothesis was confirmed, but
it was only the first layer.

**Then it came back on RP2350 (2026-08-12).** The line above — "Neither
reproduces on RP2350" — stopped being true two days later, exactly along the
axis the [Residual](#residual-not-bugs-today-worth-knowing) section named. Same
symptom pair, same flash-write path, different route into the same lockup; see
[RP2350 recurrence](#rp2350-recurrence-2026-08-12) at the end.

## Run environment

- Board `testbench_rp2040`, RP2040 (dual-core Cortex-M0+), 2 MB flash, 264 KB RAM.
- Probe: CMSIS-DAP Debug Probe `2e8a:000c`, SWD. RP2040 is multidrop SWD; a
  `Failed to switch to DP Multidrop(11002927)` warning from probe-rs is **benign
  noise** and appears on successful runs too.
- Firmware: `--release`. `scripts/hil-run.sh` hardcodes `--chip RP235x`, so it
  cannot drive this board; drive `probe-rs` directly.
- Commits tested: `dcb377c` (then-HEAD) and `e44b879` (attribution baseline).

```bash
# build + flash + stream RTT (foreground; `timeout` ends the RTT capture).
# Do NOT wrap in setsid — it detaches and holds the USB claim, and the next
# attempt then fails with "Failed to open probe".
bash scripts/build.sh --board testbench_rp2040 --app helloworld --release
timeout 90 probe-rs run --chip RP2040 --protocol swd \
  target/thumbv6m-none-eabi/release/picodroid

# between attempts, always:
pkill -x probe-rs    # -x, not -f: `pkill -f probe-rs` matches your own shell
sleep 2

# PDB (device must be running and enumerated)
cargo build --release --manifest-path tools/pdb/Cargo.toml
target/release/pdb ping
target/release/pdb sysmon
target/release/pdb install build/apks/helloworld.papk
```

## RP40-1 — LittleFS runtime File I/O hangs; `bootcount` produces no output · **pre-existing**

### Symptom

`bootcount` flashes and boots, then emits **nothing at all** over RTT — no log
line, no panic — for 90 s. `helloworld`, same board, same build settings, same
session, logs normally.

### Why this means "hangs inside File I/O" rather than "filesystem is broken"

`bootcount` reads a counter, writes it back, then logs:

```java
int count = readCount() + 1;   // File.exists + FileInputStream.read
writeCount(count);             // FileOutputStream.write
Log.i(TAG, "Boot #" + count);  // never reached
```

A *failed* filesystem still reaches the log: `readCount` returns 0 when
`exists()` is false or the read is short, and `writeCount`'s failure is
discarded. The app would print `Boot #1` every boot. Printing nothing means
control never returns from the File path.

### Repro

```bash
bash scripts/build.sh --board testbench_rp2040 --app bootcount --release
pkill -x probe-rs; sleep 2
timeout 120 probe-rs run --chip RP2040 --protocol swd \
  target/thumbv6m-none-eabi/release/picodroid
# expected on a healthy board: "[INFO ] BootCount: Boot #N"
# actual: flash completes ("Finished in 29.30s"), then silence
```

### Attribution

Reproduced at `e44b879` — the commit *before* the `Rtos`/filesystem work — by
checking that commit out, rebuilding, and reflashing. Identical silence. The
filesystem move (`725a2b7`) is **not** the cause.

On RP2350 the same app works: `Boot #229` then `#230` across a reflash,
exercising read and write.

## RP40-2 — `pdb install` times out during erase and the device drops off USB · **pre-existing**

### Symptom

```
Installing build/apks/helloworld.papk (1 KB)...
Erasing flash (~10-15 s)...
error: waiting for READY: Operation timed out
```

Afterwards the device no longer enumerates; subsequent `pdb` calls report
`no picodroid devices found`. It recovers with an SWD reflash (`probe-rs run`),
so the MCU is not bricked.

### Repro

Flash `helloworld --release`, confirm `pdb ping` answers, then:

```bash
target/release/pdb install build/apks/helloworld.papk
```

### Attribution

Reproduced at `e44b879` by the same rebuild-and-reflash method. Not from the
extraction work. B7/B9 record installs passing on RP2350 (four consecutive
after stage 3a, three after 3c), so this is rp2040-specific.

## Shared hypothesis

**Both failures are the first flash *write* the firmware attempts at runtime**
— LittleFS's program/erase for RP40-1, the installer's erase for RP40-2. Reads
are fine (the app boots from XIP; `ping`/`sysmon` work).

The obvious candidate on this chip is the **dual-core XIP-disable hazard**:
`with_xip_disabled!` stops execute-in-place while a ROM flash routine runs, and
any code fetching instructions from flash on the *other* core during that window
faults or hangs. The sysmon dump above shows `IDLE1` **Ready on core 1** — so
core 1 is not parked. RP2350 not reproducing is consistent with the two chips'
differing SMP ports rather than with anything application-level.

This is a hypothesis chosen to be falsifiable, not a diagnosis. Check it first,
but do not assume it.

### First checks

1. **Is core 1 the problem?** Confirm what `IDLE1` executes from during the
   XIP-disable window, and whether the RP2040 port parks or stalls core 1 at
   all. Compare against the RP2350 port, which does not reproduce.
2. **Does it hang or fault?** Attach with gdb rather than inferring from
   silence — `probe-rs gdb` plus `gdb-multiarch`, per
   `reference_gdb_sim_debugging` and the boot-autopilot recipe. A hard fault in
   the flash routine and a spin waiting for a flag look identical over RTT.
3. **Narrow RP40-1 to the operation.** LittleFS mounts fine (boot does not
   fail), so a read path works. Establish whether it is the first `erase`, the
   first `prog`, or neither, by instrumenting `platforms/rp/src/fs/storage.rs`.
4. **Does the priority inversion matter?** The `fs` task is PRI 22, *above* the
   `pdb` task at 21, and both are pinned to core 0. That ordering is worth
   double-checking against the install park handshake even though `fs` should be
   blocked throughout.

### Ruled out

- **Not the extraction work** (stages 4–5). Both reproduce at `e44b879`.
- **Not a missing or misconfigured FS region.** `platforms/rp/mcus/rp/rp2040.x`
  defines `FS_FLASH` at `0x100E0000`, 128 K, with `__fs_start`/`__fs_end`
  exported, and `FLASH` bounded to `896K - 0x100` so an overflow would be a link
  error rather than a silent overlap.
- **Not RTT or probe setup.** `helloworld` streams RTT on the same board,
  build profile and probe invocation.
- **Not the multidrop warning.** It appears on successful runs too.

### Adjacent hazard, worth fixing regardless

The rp2040 `--release` image is **908,617 bytes against a 917,248-byte program
region — 99.1% full, ~8.6 KB spare.** `scripts/build.sh` reports this as
`Flash: 908621 / 2097152 bytes (43%)`, measuring against total flash rather than
the `FLASH` region the image actually lives in. The linker still enforces the
real ceiling, so this cannot cause silent corruption, but the reported figure
gives no warning before a build starts failing to link. Consider reporting the
region-relative number.

## Resolution (2026-08-10)

One symptom-pair, three cooperating causes. All fixed in one pass; the
verification recipes above were run to the letter on `testbench_rp2040`.

### Cause 1 — core 1 takes the tick mid-XIP-window (the shared hypothesis, confirmed)

On RP2040 the FreeRTOS tick runs on core 1 (`configTICK_CORE=1`), and
`with_xip_disabled!` masks interrupts **only on the calling core**. A sector
erase is ~45 ms against a 1 kHz tick, so core 1 was guaranteed to take a
SysTick inside the window; exception entry reads the vector table from the
flash the ROM routine had just disconnected, the fetch faults, the HardFault
vector fetch faults too, and core 1 hits LOCKUP — killing the tick core and
the scheduler with it. First runtime flash write = first hang, exactly as
observed for both LittleFS (RP40-1) and the installer erase (RP40-2).

**Fix:** pico-sdk-style lockout, as a task — `platforms/rp/src/hal/rp/
core1_park.rs`. A `flashpark` task (priority 30 = `PRIORITY_FLASH_PARK`,
pinned core 1) blocks on a notification; `flash_erase_range`/
`flash_program_range` acquire a guard that wakes it, waits until core 1 is
spinning in a single-`asm!`-block RAM (`.data`) loop with interrupts masked,
runs the ROM operation, then releases. Codegen audited by objdump: nothing
core 1 executes during the window leaves SRAM.

### Cause 2 — `configRUN_MULTIPLE_PRIORITIES` defaulted to 0 (found by gdb, not by the doc)

The first parker build still hung — differently. SRAM told the story:
`PARK_REQUESTED=1, PARKED=1`, core 1 parked as designed, and core 0 sitting
in the **idle task** with fs Ready at priority 22 and no yields pending. The
FreeRTOS SMP kernel's default `configRUN_MULTIPLE_PRIORITIES=0` (absent from
our FreeRTOSConfig.h) forbids tasks of *different* priorities running on
both cores at once — so the moment the priority-30 parker ran on core 1, the
priority-22 fs task was barred from core 0 and could never clear the park
request. Mutual deadlock by scheduler policy.

**Fix:** RP2040 branch of `FreeRTOSConfig.h` sets
`configRUN_MULTIPLE_PRIORITIES=1` and pins the timer service to core 0
(`configTIMER_SERVICE_TASK_CORE_AFFINITY`), and `glue.rs`'s generic spawn
arm now pins to core 0 (the sensor sampler and jvm-bg workers were spawned
unpinned — under real SMP they would race the single-core JVM heap). Net:
the only concurrency unlocked is parker-vs-core-0, which is the point.
RP2350 keeps the kernel default untouched.

### Cause 3 — per-core VTOR left one core's IPI handler dead (latent, prerequisite)

Both pico shims kept one RAM vector table but redirected `VTOR` only on
whichever core first called `irq_set_exclusive_handler` — VTOR is
**per-core**, so the other core stayed on the flash table, whose SIO-FIFO
(RP2040) / doorbell (RP2350) slot is cortex-m-rt's DefaultHandler infinite
loop. Invisible until now because every app task is core-0-pinned and no
cross-core yield IPI ever fired on these benches; the parker's wake is
exactly such an IPI. Both `multicore_launch_core1`s now initialise the RAM
table up front and launch core 1 pointing at it. (RP2350 shim fixed
identically; hardware-verified 2026-08-11, see below.)

### Verified

- RP40-1 recipe: `bootcount` prints `Boot #1`, and `Boot #2` after a
  reflash — read **and** write, persisted across reboot.
- RP40-2 recipe: three consecutive `pdb install helloworld.papk` complete
  (erase → stream → reboot) and `pdb ping` still answers afterwards.
- `helloworld` RTT unchanged; `pdb sysmon` shows `flashpark` Blocked at 30,
  stack HWM 216/256 words.
- Sim smoke (helloworld/benchmark/blinky) and the full pre-commit suite.
- **RP2350 regression sweep (2026-08-11, `pico_enviro_mon`)** — the shim
  VTOR fix and the glue.rs pinning also ship to RP2350, so the same recipes
  were re-run there: `helloworld` boots and logs; `bootcount` `#271 → #272`
  across a reflash; three consecutive `pdb install` + `ping`; `sysmon`
  normal (11 tasks, no `flashpark` — rp2040-only by design); `picoenvmon`
  boots to Home.onCreate with the sensor task up and no lifecycle errors.

### Adjacent items also done

- `build.sh` now reports flash against `LENGTH(FLASH)` from the linker
  script (99% real usage, previously reported as 43% of chip total), with
  the chip total alongside.
- `hil-run.sh` now derives the probe-rs chip from the board's MCU
  (`resolve_board` sets `PROBE_CHIP`), so it can drive `testbench_rp2040`.

### Residual (not bugs today, worth knowing)

> **Both bullets below were overtaken by events on 2026-08-12** — the first
> became the bug described in [RP2350 recurrence](#rp2350-recurrence-2026-08-12),
> and the second was resolved by the same change. Kept verbatim because the
> first one called the shot.

- RP2350 still runs flash windows without parking core 1. It survives
  because its tick is on core 0 and a quiescent core 1 stays inside the XIP
  cache — cache-luck, not a guarantee. If RP2350 ever grows a core-1 task
  that runs during flash writes, give it the parker too.
- With `configRUN_MULTIPLE_PRIORITIES=0` still in force on RP2350, the
  cyw43 task on Pico 2 W serialises against every different-priority core-0
  task rather than running in parallel as its spawn comment intends.

## RP2350 recurrence (2026-08-12)

### Symptom

The 2026-08-12 nightly HIL on `testbench_rp2350` failed `prefs_demo` (both
modes) and `blinky:pdb-install-stress` (both modes) — RP40-1 and RP40-2
respectively, on the chip that was supposed to be immune. The tell that this
was not the old bench flakiness was the **variance**: across four runs the same
binary produced 0/10, 5/10, a passing lone `pdb install`, and a failing one.
`prefs_demo` hung at a different subtest depending on shrink mode (first write
in no-shrink, `testClear()` in shrink). Deterministic bugs do not do that.

`bootcount` kept passing throughout — one short write is a small target.

### Root cause — the residual hazard, activated

Read off the hung device with `probe-rs gdb` (recipe below). Core 1:

```
PC   = 0xeffffffe   xPSR IPSR = 3      <- ARM LOCKUP, inside HardFault
stacked frame at MSP 0x20009770:
  R12 = 0x12121212  LR = 0x10069d1b
  PC  = 0x1006a098  = vTaskSwitchContext + 1000
  xPSR= 0x2100000e  -> IPSR = 14 = PendSV
```

Core 1 was running `vTaskSwitchContext` — **flash-resident** — inside a PendSV,
while core 0 had XIP disconnected. Instruction fetch bus-faults, the HardFault
handler is also in flash so its fetch faults too, LOCKUP. Identical to Cause 1,
reached by a different exception: RP2040 gets there via its core-1 tick, RP2350
via the PendSV that core 0's yield IPI raises.

The knock-on explains the freeze: `vTaskSwitchContext` runs holding the
FreeRTOS task spinlock, which a locked-up core never releases. Core 0 wedges at
its next critical section — observed as `spin_lock_unsafe_blocking` ←
`vPortRecursiveLock` ← `vTaskEnterCriticalFromISR` ← `isr_systick`.

**Why now:** `d66882b` (WiFi bring-up) fixed the RP2350 SIO doorbell registers,
which had pointed at INTERP1 where writes are discarded. Until then every
cross-core wake IPI was a silent no-op, so core 1 never took a PendSV and the
hazard could not fire. The `0a05896` VTOR change is what made core 1's handlers
live at all. Neither commit is wrong; together they removed the cache-luck.

### Fix

Extend the parker from `chip-rp2040` to all of `family-rp` — it was already the
right mechanism, just gated too narrowly:

- `hal/rp/mod.rs`, `hal/mod.rs` — un-gate the module and its re-export.
- `boot_tasks.rs` — create `flashpark` on both chips.
- `boot_budget.rs` — un-gate `FLASHPARK_STACK_WORDS` and its `BOOT_TASKS` row
  (+1 KB on RP2350).
- `flash.rs` — `flash_erase_range` / `flash_program_range` park unconditionally.
- `mcus/rp/FreeRTOSConfig.h` — `configRUN_MULTIPLE_PRIORITIES 1` and
  `configTIMER_SERVICE_TASK_CORE_AFFINITY` move out of the RP2040-only `#else`.

That last one is **load-bearing, not tidying**: with the kernel default of 0,
the priority-30 parker on core 1 bars the priority-22 fs task from core 0 and
the park request can never be cleared. Enabling the parker without it converts
this bug into Cause 2's deadlock. It also resolves the second Residual bullet.

### Collateral: cyw43 had to come off core 1

`configRUN_MULTIPLE_PRIORITIES=1` broke DHCP on `testbench_rp2350w`. Symptom:
link comes up, endpoint stays at **0.0.0.0**, no recovery over 3 minutes —
but only when the app keeps core 0 busy. `blinky` failed 4/4; `netdemo`, which
mostly waits, bound normally every time, which is what made it look app-specific
rather than scheduler-specific.

Bisected against a stashed tree: the parker is not involved (disabling just the
two `park_core1_for_flash` calls still reproduces), `configTIMER_SERVICE_TASK_
CORE_AFFINITY` is not involved, and `ipconfigIP_TASK_PRIORITY` is not the lever
either — raising it 7 → 21 changed nothing. What fixes it is pinning the cyw43
task to **core 0** (`boot_tasks.rs`), which it should have been all along: every
other task on this family already is, and its core-1 pin was justified only as
"keeps core 0 free for JVM/UI".

So there is a **real, still-unfixed race in the cyw43 / FreeRTOS+TCP glue** that
appears when the driver task genuinely overlaps a different-priority core-0
task. `configRUN_MULTIPLE_PRIORITIES=0` had been hiding it by making that
overlap impossible; the pin hides it again by the same logic. Worth hunting
properly before anything is deliberately scheduled onto core 1 on a WiFi board.
It also makes the park window safer: core 1 is now the parker's alone.

### Verified

On `testbench_rp2350`:

- `prefs_demo` `19 passed, 0 failed` / `=== ALL PASSED ===` — including
  `testClear()`, the shrink-mode hang point.
- `blinky:pdb-install-stress` **10/10**, at 5 s/cycle — matching the 2026-08-10
  known-good run exactly, so this restores the original timing rather than
  changing it. (Pre-fix successful cycles crawled at ~44 s: the limp was itself
  a symptom.)
- Full HIL suite **49 PASS / 0 FAIL / 0 ERROR**, identical to the last
  known-good run.

On `testbench_rp2350w` (Pico 2 W), which is the board that actually has a
core-1 task to park:

- `helloworld` boots, cyw43 firmware loads (7.95.49).
- `bootcount` **#288 → #289** across a reflash — LittleFS write with the WiFi
  task live.
- **10/10** `pdb install` cycles with the parker active and WiFi associated.
- `netdemo` joins + DHCP `192.168.4.94` in 5–6 s, before and after those 10
  installs.

### Debugging notes for next time

- A locked-up core will not answer memory reads to its own SCS (`0xE000ED28`
  CFSR/HFSR are unreadable). Read its **stacked exception frame from the other
  core** instead — SRAM is shared — after taking `$msp` from the dead core.
  That frame's `PC`/`IPSR` is what identifies the fault.
- Do not trust argument values in inlined frames of an optimized build. Core 0's
  backtrace showed `write_bytes(dst=ucHeap+8228, count=4294967295)` inside
  `lfs_cache_zero`, which reads as a 4 GB memset over all of SRAM. It is an
  artifact — the real `cache_size` is fine, and chasing it would have been a
  day spent on a nonexistent heap-corruption bug.
- `scripts/hil-run.sh` runs `pkill -f "probe-rs"` internally, which kills any
  wrapper shell whose command line contains that string (exit 144). Launch it
  bare.
