# Bug backlog: rp2040 runtime-flash failures — 2026-08-01

Two failures found on a real **testbench_rp2040** board (RP2040, Waveshare 2.8"
Pico display) when the rp2040 half of the HIL gate was run for the first time.
Both sit on the **runtime flash-write path**, and both are **pre-existing** —
they reproduce identically at `e44b879`, before the work that surfaced them.
Neither reproduces on RP2350.

Each section is self-contained: symptom, evidence, repro, attribution, and what
to check first. RP40-1 and RP40-2 are probably one root cause (see
[Shared hypothesis](#shared-hypothesis)) and are best worked together.

**Status: not investigated.** What follows is observation plus one hypothesis,
deliberately separated. Nothing here has been root-caused.

## Run environment

- Board `testbench_rp2040`, RP2040 (dual-core Cortex-M0+), 2 MB flash, 264 KB RAM.
- Probe: CMSIS-DAP Debug Probe `2e8a:000c`, SWD. RP2040 is multidrop SWD; a
  `Failed to switch to DP Multidrop(11002927)` warning from probe-rs is **benign
  noise** and appears on successful runs too.
- Firmware: `--release`. `scripts/hil-run.sh` hardcodes `--chip RP235x`, so it
  cannot drive this board; drive `probe-rs` directly.
- Commits tested: `dcb377c` (then-HEAD) and `e44b879` (attribution baseline).

```bash
# build + flash + stream RTT (foreground; `timeout` ends the RTT capture).
# Do NOT wrap in setsid — it detaches and holds the USB claim, and the next
# attempt then fails with "Failed to open probe".
bash scripts/build.sh --board testbench_rp2040 --app helloworld --release
timeout 90 probe-rs run --chip RP2040 --protocol swd \
  target/thumbv6m-none-eabi/release/picodroid

# between attempts, always:
pkill -x probe-rs    # -x, not -f: `pkill -f probe-rs` matches your own shell
sleep 2

# PDB (device must be running and enumerated)
cargo build --release --manifest-path tools/pdb/Cargo.toml
target/release/pdb ping
target/release/pdb sysmon
target/release/pdb install build/apks/helloworld.papk
```

## What works on this board

Established at `dcb377c`, so these are not suspects:

| Check | Result |
|---|---|
| `helloworld` boot + RTT | passes |
| `pdb ping` | `picodroid/2.1`, max PAPK 1020 KB |
| `pdb sysmon` | 11 tasks decode correctly |

Normal rp2040 boot output over RTT is **just the app's own log line** — there is
no boot chatter — so "one line, then nothing" is success, not truncation.

The `sysmon` task table, which is the useful reference for both bugs:

## RP40-1 — LittleFS runtime File I/O hangs; `bootcount` produces no output · **pre-existing**

### Symptom

`bootcount` flashes and boots, then emits **nothing at all** over RTT — no log
line, no panic — for 90 s. `helloworld`, same board, same build settings, same
session, logs normally.

### Why this means "hangs inside File I/O" rather than "filesystem is broken"

`bootcount` reads a counter, writes it back, then logs:

```java
int count = readCount() + 1;   // File.exists + FileInputStream.read
writeCount(count);             // FileOutputStream.write
Log.i(TAG, "Boot #" + count);  // never reached
```

A *failed* filesystem still reaches the log: `readCount` returns 0 when
`exists()` is false or the read is short, and `writeCount`'s failure is
discarded. The app would print `Boot #1` every boot. Printing nothing means
control never returns from the File path.

### Repro

```bash
bash scripts/build.sh --board testbench_rp2040 --app bootcount --release
pkill -x probe-rs; sleep 2
timeout 120 probe-rs run --chip RP2040 --protocol swd \
  target/thumbv6m-none-eabi/release/picodroid
# expected on a healthy board: "[INFO ] BootCount: Boot #N"
# actual: flash completes ("Finished in 29.30s"), then silence
```

### Attribution

Reproduced at `e44b879` — the commit *before* the `Rtos`/filesystem work — by
checking that commit out, rebuilding, and reflashing. Identical silence. The
filesystem move (`725a2b7`) is **not** the cause.

On RP2350 the same app works: `Boot #229` then `#230` across a reflash,
exercising read and write.

## RP40-2 — `pdb install` times out during erase and the device drops off USB · **pre-existing**

### Symptom

```
Installing build/apks/helloworld.papk (1 KB)...
Erasing flash (~10-15 s)...
error: waiting for READY: Operation timed out
```

Afterwards the device no longer enumerates; subsequent `pdb` calls report
`no picodroid devices found`. It recovers with an SWD reflash (`probe-rs run`),
so the MCU is not bricked.

### Repro

Flash `helloworld --release`, confirm `pdb ping` answers, then:

```bash
target/release/pdb install build/apks/helloworld.papk
```

### Attribution

Reproduced at `e44b879` by the same rebuild-and-reflash method. Not from the
extraction work. B7/B9 record installs passing on RP2350 (four consecutive
after stage 3a, three after 3c), so this is rp2040-specific.

## Shared hypothesis

**Both failures are the first flash *write* the firmware attempts at runtime**
— LittleFS's program/erase for RP40-1, the installer's erase for RP40-2. Reads
are fine (the app boots from XIP; `ping`/`sysmon` work).

The obvious candidate on this chip is the **dual-core XIP-disable hazard**:
`with_xip_disabled!` stops execute-in-place while a ROM flash routine runs, and
any code fetching instructions from flash on the *other* core during that window
faults or hangs. The sysmon dump above shows `IDLE1` **Ready on core 1** — so
core 1 is not parked. RP2350 not reproducing is consistent with the two chips'
differing SMP ports rather than with anything application-level.

This is a hypothesis chosen to be falsifiable, not a diagnosis. Check it first,
but do not assume it.

### First checks

1. **Is core 1 the problem?** Confirm what `IDLE1` executes from during the
   XIP-disable window, and whether the RP2040 port parks or stalls core 1 at
   all. Compare against the RP2350 port, which does not reproduce.
2. **Does it hang or fault?** Attach with gdb rather than inferring from
   silence — `probe-rs gdb` plus `gdb-multiarch`, per
   `reference_gdb_sim_debugging` and the boot-autopilot recipe. A hard fault in
   the flash routine and a spin waiting for a flag look identical over RTT.
3. **Narrow RP40-1 to the operation.** LittleFS mounts fine (boot does not
   fail), so a read path works. Establish whether it is the first `erase`, the
   first `prog`, or neither, by instrumenting `platforms/rp/src/fs/storage.rs`.
4. **Does the priority inversion matter?** The `fs` task is PRI 22, *above* the
   `pdb` task at 21, and both are pinned to core 0. That ordering is worth
   double-checking against the install park handshake even though `fs` should be
   blocked throughout.

### Ruled out

- **Not the extraction work** (stages 4–5). Both reproduce at `e44b879`.
- **Not a missing or misconfigured FS region.** `platforms/rp/mcus/rp/rp2040.x`
  defines `FS_FLASH` at `0x100E0000`, 128 K, with `__fs_start`/`__fs_end`
  exported, and `FLASH` bounded to `896K - 0x100` so an overflow would be a link
  error rather than a silent overlap.
- **Not RTT or probe setup.** `helloworld` streams RTT on the same board,
  build profile and probe invocation.
- **Not the multidrop warning.** It appears on successful runs too.

### Adjacent hazard, worth fixing regardless

The rp2040 `--release` image is **908,617 bytes against a 917,248-byte program
region — 99.1% full, ~8.6 KB spare.** `scripts/build.sh` reports this as
`Flash: 908621 / 2097152 bytes (43%)`, measuring against total flash rather than
the `FLASH` region the image actually lives in. The linker still enforces the
real ceiling, so this cannot cause silent corruption, but the reported figure
gives no warning before a build starts failing to link. Consider reporting the
region-relative number.

## How to verify a fix

```bash
# RP40-1
bash scripts/build.sh --board testbench_rp2040 --app bootcount --release
timeout 120 probe-rs run --chip RP2040 --protocol swd \
  target/thumbv6m-none-eabi/release/picodroid   # expect "Boot #N"
# reflash; expect N+1 — that is the check that read AND write both work
```

```bash
# RP40-2 — three consecutive installs, matching the rp2350 gate in B7/B9
for i in 1 2 3; do target/release/pdb install build/apks/helloworld.papk; sleep 3; done
target/release/pdb ping    # device still answers afterwards
```

Then run the rp2040 half of the HIL gate properly. Note that `hil-run.sh` is
RP235x-only today; teaching it the chip is part of the job if this board is to
stay covered.
